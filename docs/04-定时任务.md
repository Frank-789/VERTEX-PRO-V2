# 定时任务

> **一句话**：往 `data/issues/` 丢一个带 `when:` 的 Markdown 文件，它就会按排期自己跑，
> 跑完把报告放到 `data/inbox/`。没有任务管理界面，也不需要。

---

## 一、一个文件就是一个任务

```markdown
---
title: 每日利润测算
when: { kind: cron, cron: "0 9 * * *", timezone: "Asia/Shanghai" }
---

帮我算一下成本 45、售价 129、拼多多平台的利润，并说明保本售价。
```

存成 `data/issues/daily-profit.md`，**文件名（去掉 `.md`）就是任务 id**。
后端 30 秒内会扫到它，第二天早上 9 点跑第一次，报告落在 `data/inbox/`。

**正文就是你平时会对它说的那句话** —— 原样交给模型，不需要学任何模板语法。
正文写空了就退回用 `title`。

### 去掉 `when:` 会怎样

它变成一张**普通看板卡片**：列在 `GET /api/v1/issues` 里，但不会被调度。
这个设计是刻意的 —— 任务清单和看板本来就是同一样东西，
不该为了「能不能定时」维护两套结构。

### frontmatter 字段

| 字段 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `when` | 否 | — | 不写就是看板卡片。写法见下节 |
| `title` | 否 | 文件名 | 只用于展示 |
| `status` | 否 | `todo` | 写成 `done` 或 `paused` 就**停止调度**，但文件保留 |
| `enabled` | 否 | `true` | 等价于总开关，写 `false` 停止调度 |

> `status: paused` 和直接删文件的区别：暂停保留历史和排期，改回 `todo` 就接着跑。

## 二、`when:` 怎么写

### 完整写法

```yaml
when: { kind: cron, cron: "0 9 * * *", timezone: "Asia/Shanghai" }
```

| 键 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `kind` | 否 | `cron` | 目前**只支持 `cron`**，写别的会明确报错（将来加 `interval` / `once` 在这里分支） |
| `cron` | 是 | — | 5 字段标准 cron |
| `timezone` | 否 | `ISSUE_DEFAULT_TZ`（默认 `Asia/Shanghai`） | IANA 时区名 |

### 简写

只写表达式就是 cron，时区走默认值：

```yaml
when: "0 9 * * *"
```

### cron 语法

5 个字段，**空格分隔**（不是 6 字段，没有「秒」）：

```
分钟  小时  日  月  星期
 0    9    *   *   *
```

| 写法 | 含义 |
|---|---|
| `*` | 任意值 |
| `5` | 就是这个值 |
| `1,15,30` | 枚举 |
| `9-17` | 范围 |
| `*/15` | 步长（每 15 分钟） |
| `1-5` | 范围，星期里表示周一到周五 |

> ⚠️ **星期是 0 = 周日**，`1` = 周一 …… `6` = 周六。
> 但写成 `7` 也是周日（cron 的老规矩，两个值都收）。

### ⚠️ 最容易搞错的一条：日和星期是 **OR**

**当「日」和「星期」两个字段同时被限制时，命中是取 OR 的** —— 这是标准 cron
的语义，也是最常被误读的一条。

```yaml
cron: "0 0 1 * 1"     # 每月 1 号 **或** 每周一，不是「既是 1 号又是周一」
```

想让「只在每月 1 号」生效，就把星期写成 `*`：

```yaml
cron: "0 0 1 * *"     # 每月 1 号 00:00
```

### 常见排期

| 想要 | 表达式 |
|---|---|
| 每天早 9 点 | `0 9 * * *` |
| 每 15 分钟 | `*/15 * * * *` |
| 工作日早 8:30 | `30 8 * * 1-5` |
| 每小时整点 | `0 * * * *` |
| 每周一早 9 点 | `0 9 * * 1` |
| 每月 1 号零点 | `0 0 1 * *` |
| 每年 2 月 29 号（闰日） | `0 0 29 2 *` |

> 最后一条是**故意留的边界用例** —— 它四年才命中一次，
> 内部用「逐级推进」而不是逐分钟扫来找下一次，跑一次不到 1 毫秒。
> （逐分钟扫的话要空转 200 多万次。）

### 写错了会怎样

**不会让服务起不来，也不会让其他任务受影响。** 出错的那条会带着 `error` 字段
出现在 `GET /api/v1/issues` 里，原因写得很直白：

```json
{ "id": "bad-task", "schedulable": false, "error": "cron 解析失败：…" }
```

覆盖到的错误：表达式字段数不对、数值越界、不认识的时区、
`when` 写成了列表、`kind` 不支持、YAML 本身不合法。
**一个文件写错只影响它自己** —— 这是从 `config.py` 沿用下来的原则。

## 三、状态为什么不在文件里

和 OpenAlice 不同的一点，**是刻意的取舍**。

Alice 把 `lastRun` 写回任务文件。我们不这么做 —— 那意味着每次跑完都要改写
一个**归用户所有、用户可能正在编辑**的文件，三个问题：

1. **和编辑器打架** —— 你正改着，它给你覆盖了
2. **文件若纳入 git 会一路噪音** —— 每跑一次一个 diff
3. **写到一半被杀，任务定义就坏了** —— 拿状态换定义，不划算

所以状态另存 `data/issues/.state.json`：

```json
{
  "version": 1,
  "issues": {
    "daily-profit": {
      "lastRun": 1790563366.93,
      "lastStatus": "ok",
      "lastDurationMs": 1862,
      "lastError": null,
      "runs": 2
    }
  }
}
```

写入用**临时文件 + `os.replace`** 原子替换 —— 直接覆盖的话，写一半掉电就只剩
半个 JSON，下次启动所有任务的状态全丢，**那意味着所有任务会立刻重跑一遍**。

`.md` 保持纯声明、归你所有；`.state.json` 是机器的账本。
**删掉 `.state.json` 是安全的**，代价只是所有任务按「从没见过」重新起算。

## 四、四个关键语义

### ① 判据是「上次跑之后有没有命中过」，不是「此刻是否命中」

这是整个设计里最要紧的一条。

如果按「此刻这一分钟是否命中」判，就**要求调度器恰好在那分钟醒着**。
进程重启、tick 延迟、机器休眠、容器被迁移 —— 任何一个都会让那一分钟被跳过，
任务就**静默漏跑**了，而且没有任何痕迹。

现在从 `lastRun` 往后推：只要那一刻已经过去，不管调度器当时在不在，都算欠着。
**天然抗重启。**

### ② 欠了多班只补跑一班，且补的是**最早**那次

一个每分钟执行的任务停机一天，欠 1440 班 —— 全补是荒谬的。
监控类任务只关心「现在」，所以**合并成一次**，其余作废。

**但补的是最早那次，不是最近那次。** 停机三天后补跑，如果补最近那次，
报告上的 `lagSeconds` 只有几秒，「停机三天」这个信息就彻底丢了；
补最早那次，报告读起来是「本该三天前跑」—— 这才是排障时要看的。

真机上验证过一次：

```yaml
scheduledAt: '2026-09-27T09:00:00+08:00'
lagSeconds: 92568          # ≈25.7 小时，正好对上前一天的 09:00 排期
```

### ③ 状态先于执行落盘（persist-before-execute）

开跑**之前**先写一次 `lastRun`。顺序反过来的话，跑到一半被杀、重启后
`lastRun` 还停在上一轮，这条任务会立刻再跑一次 —— **崩溃即死循环**。

代价是崩溃那次算「跑过了」，漏一班。**宁可漏，不可循环。**

### ④ 新建的任务不会立刻跑

从没见过（`lastRun` 为空）时，起点取**文件自己的修改时间**（mtime）。
含义是：新建一个「每天早上 9 点」的任务，它等到明天 9 点才跑，
而不是一丢进去就立刻跑一次。

这是最少意外的行为。想立刻看效果就用下面的手动触发。

## 五、报告落在 `data/inbox/`

**无论成功还是失败都会写报告** —— 失败也是结果，静默失败才是最糟的。

文件名格式 `YYYY-MM-DDTHHMMSS-<任务id>.md`，**文件名本身即索引**，
按文件名倒序就是时间倒序（不按 mtime —— 复制文件会让 mtime 失真）。

```markdown
---
issue: daily-profit
title: 每日利润测算
runAt: '2026-09-28T02:42:48.793314+00:00'
durationMs: 1862
ok: true
steps: 1
tools:
- profit.calc
turn: d655bc7d2988
scheduledAt: '2026-09-27T09:00:00+08:00'
lagSeconds: 92568
---

（模型的原话，和聊天里看到的完全一样）
```

| 字段 | 说明 |
|---|---|
| `runAt` | 实际开始执行的时刻（UTC） |
| `scheduledAt` | **本来该跑的时刻**（带任务的时区）。手动触发时为 `null` |
| `lagSeconds` | 上面两者之差。**排障时第一个看这个** —— 大得离谱说明停机过 |
| `tools` | 这轮调了哪些工具 |
| `turn` | 事件日志里的 turn id，可以 `grep` 到完整过程（见 [03-配置参考.md](03-配置参考.md#七data-目录里有什么)） |
| `ok` | 执行是否成功。失败时正文是错误说明，不是空的 |

文件名时间戳**只精确到秒**，同一秒内的两次运行（定时 + 手动触发）会撞名 ——
撞了就加 `-2` / `-3` 后缀，**绝不覆盖**。两份报告都留着。

## 六、怎么用

### 手动触发一次（不等排期）

```bash
curl -X POST localhost:8000/api/v1/issues/daily-profit/run
```

走的是和定时**完全相同**的执行路径，所以也会更新 `lastRun` ——
否则手动跑完，下一分钟定时又会再跑一次。

| 状态码 | 含义 |
|---|---|
| `200` | 跑完了，返回和报告同样的元信息 |
| `400` | id 不合法（含路径穿越）—— 这是格式问题，不是「找不到」 |
| `404` | 没有这个任务文件 |
| `409` | 上一次还在跑。**这不是错误，是「你等它跑完」** |

### 看任务清单

```bash
curl -s localhost:8000/api/v1/issues | python3 -m json.tool
```

返回里带 `scheduler` 块（是否在跑、本轮正在执行哪些、上次出错没有），
每条任务带 `cron` / `schedule`（人话版）/ `nextRun` / `lastRun` / `runs`。

```json
{
  "id": "daily-profit",
  "schedule": "[9] 点 [0] 分",
  "nextRun": "2026-09-29T09:00:00+08:00",
  "lastStatus": "ok",
  "runs": 2
}
```

### 看报告

```bash
curl -s "localhost:8000/api/v1/inbox?limit=10" | python3 -m json.tool   # 清单
curl -s localhost:8000/api/v1/inbox/2026-09-28T024248-daily-profit.md   # 全文
ls -t data/inbox/ | head                                                # 直接翻文件也行
```

### 关掉调度器

```bash
ISSUE_SCHEDULER=0        # 只保留手动触发
```

**测试环境务必设成 0** —— 否则后台循环会在断言之间插进来执行任务。
`apps/api/tests/test_smoke.py` 顶部就是这么做的。

其余开关（扫描间隔、单轮上限、默认时区）见
[03-配置参考.md](03-配置参考.md#定时任务)。

## 七、为什么是「进程内的一个循环」

没有 Celery，没有 Redis，没有独立的 cron 服务。这个项目的部署形态本来就是
「跑起来就不停」（见 [02-部署指南.md](02-部署指南.md) 第四节），
任务定义又已经是文件了 —— 再加一套需要单独运维的调度基础设施，
换来的只是「分布式」，而我们只有一台机器。

真到了要横向扩的那天，换掉的成本也不高：**因为真相在文件里**，
迁移只是换一个读文件的进程。

几个工程细节：

- **扫描间隔（默认 30 秒）不是精度问题。** 任务最多晚 30 秒被发现，
  代价仅此而已 —— 判据是「上次跑之后有没有命中过」，晚发现不会漏跑。
- **单轮上限（默认 5 个）** 防止机器睡一夜醒来，二十个任务同时开跑
  把供应商的并发配额一次打满。没轮到的下一轮继续，**任务欠着不会丢**。
- **同一个任务不会重入** —— 上一次没跑完，这次直接跳过（手动触发则返回 409）。
- **循环里的异常绝不外抛。** 一次扫描失败不能把整个调度器带走；
  错误记进 `scheduler.lastError`，下一轮接着来。
- **`tick_once()` 和后台循环是分开的。** 一次完整的、可断言的调度决策，
  测试直接调它，不用和后台时序搏斗；真出问题时也是先手动调它定位。

> ⚠️ **这意味着后端必须跑在常驻进程里。** 放到 Serverless 上，
> 任务不会丢（定义在文件里），但**不会按点跑** —— 实例回收后循环就没了。

## 八、安全

- **任务 id 在读入口和写入口都卡白名单**（`^[A-Za-z0-9_-]{1,64}$`）。
  只卡读入口是不够的 —— 一个带 `../` 的 id 在**写入报告时**就已经把文件
  放到 `data/inbox/` 外面去了。
- **`POST /issues/{id}/run` 会真实执行、真实花额度。**
  后端目前无鉴权（所以端口只绑回环），**这条端点是不要对公网开放的理由之一**。
- 任务正文会原样交给模型，也会落进 `sessions/` 和 `event-log/`。
  **别把密钥写进任务文件。**
