# Vertex 架构重构方案

> 对标仓库：[TraderAlice/OpenAlice](https://github.com/TraderAlice/OpenAlice)
> 本文档基于对 OpenAlice 仓库（master 分支，v0.93.1-beta，2026-09-13 最后推送）与本地 `VERTEXpro`（→ `Frank-789/VERTEX-pro`，15 commits）的**实测盘点**，不含推测。
> 编写日期：2026-09-14

---

## 0. 结论摘要

三句话：

1. **OpenAlice 和我们不是同类产品**。它是本地优先的「交易智能体桌面/服务端应用」，我们是「电商经营智能体 Web 应用」。**能学的是架构模式，不是功能**——照搬功能会把 Vertex 变成炒股软件。

2. **"他没部署 Vercel" 这个判断不准确**。OpenAlice 仓库根目录**有** `vercel.json`，但它只把前端 UI 编译成一个**纯静态演示壳**（`build:demo` → `ui/dist` → SPA rewrite），**不含任何后端**。真正的产品通过 Docker / 桌面安装包 / CLI 分发。所以正确的学习点是：**Vercel 只承载 UI，智能体运行时永远不能跑在 Serverless 上**。

3. **我们当前最该修的不是"架构不够像 OpenAlice"，而是四个阻断级问题**：密钥泄露、无持久化、无鉴权、AI 调用绕过后端。这些不修，架构再漂亮也上不了台面。

## 1. 事实核查：OpenAlice 到底是什么

### 1.1 体量与定位

| 指标 | 数值 |
|---|---|
| Star / Fork | 7,067 / 1,125 |
| 许可证 | **AGPL-3.0**（强 copyleft，含网络条款） |
| 文件数 | 3,541 blobs |
| 仓库体积 | ~60 MB |
| 默认分支 | `master`（不是 `main`） |
| 官网 | openalice.ai，另有 Discord / QQ / X |
| 定位 | "Your one-person Wall Street" —— 覆盖股票、加密、商品、外汇、宏观 |

### 1.2 进程拓扑（这是它真正的架构）

它不是"一个 Web 应用"，而是一个**被 Guardian 监管的多进程系统**：

```text
Guardian（监管进程：锁、健康检查、重启、接管）
├── Alice          —— 主服务进程，Web UI + API + ToolCenter + 文件态
├── UTA            —— 统一交易账户，券商连接与下单权威
├── Connector Svc  —— 可选的外部通知适配器
└── Agent Runtime  —— 每个会话一个独立 PTY 子进程（claude / codex / cursor / …）
```

关键点：**Alice 会 spawn 子进程**（把 `claude`、`codex` 等 CLI 拉起成 PTY），**状态全部落在文件系统**（`~/.openalice`，Workspace 是目录 + Git 仓库）。

### 1.3 部署面（回应"他部署在哪"）

OpenAlice 有四个分发面，**没有"Serverless 后端"这一面**：

| 面 | 产物 | 备注 |
|---|---|---|
| Vercel | **纯静态 UI 演示壳** | `build:demo --filter=open-alice-ui` → `ui/dist`，rewrites 全量指向 `index.html`。**无 API、无运行时** |
| 桌面端 | Electron 安装包 | 通过 GitHub Releases 分发（macOS / Windows） |
| CLI | Bun 编译的单文件可执行程序 | `install` / `install.ps1` |
| Docker | 镜像 + compose | 端口 **47331**，**仅 loopback**，`/app` 只读 + `/data` 持久卷，首启打印一次性 admin token |

Docker 拓扑：

```text
tini (PID 1)
└── scripts/guardian/prod.mjs
    ├── Alice HTTP + Workspace
    ├── optional UTA
    └── optional Connector Service
/app   不可变镜像资源
/data  持久化运维状态与 Workspace
```

官方明确警告：**不要把 47331 裸暴露公网**，要走 HTTPS 反代或 SSH 隧道；`OPENALICE_DISABLE_AUTH=1` 禁止在远程使用。

**结论**：OpenAlice 是"自托管 / 本地优先"哲学，我们是"公有云 SaaS"哲学。这是路线差异，不是水平差异。

### 1.4 一个必须知道的事实：它的架构在快速迭代

`docs/event-system.md` 标题就是 **"Event System (Retired)"**——OpenAlice **已经废弃了事件总线**（producer/listener 拓扑、webhook task-ingest API 全部删除），改为**基于文件的 Workspace Issue 自调度**：

```markdown
---
title: Pre-market brief
status: todo
assignee: "@new-then-resume"
when: { kind: cron, cron: "30 8 * * 1-5", timezone: America/New_York }
---
（正文即给 Agent 的指令）
```

一个文件同时扮演两个角色：**去掉 `when` 是看板任务，带上 `when` 就是自调度定时任务**。没有中央任务库，没有独立调度定义。

> ⚠️ 这条对我们的启发极大（详见 §6 Phase 3），同时也说明：**别追着它的实现跑，要学它"为什么这样设计"**。

## 2. 我们的现状体检（实测，非推测）

### 2.1 基本盘

| 项 | 现状 |
|---|---|
| 前端 | Next.js 16.2.7 / React 19 / Tailwind v4 / Zustand 5 / SWR |
| 后端 | FastAPI + Uvicorn，Python 3.11，**2,784 行** |
| 页面 | 6 个：`/`、`/chat`、`/market-lab`、`/creative-studio`、`/store-pilot`、`/data-crawler`、`/settings` |
| 部署 | Vercel（前端）+ Render（后端 Docker） |
| 数据库 | **没有**。零 ORM、零迁移、零 Supabase |
| 鉴权 | **没有**。所有端点无鉴权 |

### 2.2 🔴 四个阻断级问题

#### 问题 1：密钥泄露（三处，最紧急）

| # | 位置 | 内容 | 暴露面 |
|---|---|---|---|
| 1 | `apps/api/.env.example`、`apps/web/.env.example` | **真实 DeepSeek key** `sk-1b1d…`（明文提交） | **公开仓库，已被爬虫收录** |
| 2 | `NEXT_PUBLIC_DEEPSEEK_API_KEY` / `NEXT_PUBLIC_KIMI_API_KEY` / `NEXT_PUBLIC_IMAGE_API_KEY` | 设计上就打包进前端 | **每一个访客的浏览器** |
| 3 | 桌面 `部署流程.txt`、`Github终端更新指令.txt` | 两个 GitHub PAT（明文） | 本机 + 终端历史 |

第 2 条最严重：`lib/imageGenerator.ts` 的 `callPlanAI()` **在浏览器里直接调 DeepSeek 和 Kimi**，密钥随 JS bundle 下发。任何人打开 DevTools 就能拿走并盗刷。

#### 问题 2：没有持久化，数据全丢

- 爬虫任务存在**模块级内存字典**：`crawler/models.py:102` `TASK_STORE: Dict[str, CrawlerTask] = {}`，注释写着 `# to be replaced with DB later`。重启即清空，多 worker 之间互相看不见。
- 对话历史、Creative Studio 状态**只在内存**，刷新即消失。
- 唯一的"持久化"是浏览器 `localStorage`——而其中 `demoDataStore.ts`（764 行）存的是**纯合成假数据**。

#### 问题 3：AI 调用绕过后端

`api/creative.py` 里有一套完整的服务端 DeepSeek→Kimi 降级逻辑，**但前端从来不调它**。前端走的是浏览器直连，两套 prompt 各写一份（`api/creative.py:88-135` 与 `ResultsPanel.tsx:80-93` 互为镜像）——改一处必忘另一处。

#### 问题 4：线上功能实际大面积失效

| 症状 | 根因 |
|---|---|
| 爬虫永远 `NEEDS_CONFIG` | `render.yaml` 的 `envVars` 完全没声明 `OXYLABS_*` / `APIFY_*` / `EBAY_API_KEY` |
| JD / 淘宝 / 1688 三个工具线上注册失败 | Dockerfile **没有** `playwright install chromium`，导入即抛异常被 try/except 吞掉 |
| 知识库 RAG 静默失效 | `knowledge/loader.py` 硬编码 macOS 路径 `~/Desktop/Vertex/知识库`，容器里不存在 |
| `render.yaml` 形同虚设 | `repo:` 仍是占位符 `https://github.com/your-username/vertex` |
| CORS 是隐性炸弹 | 前后端跨域，`ALLOWED_ORIGINS` 标了 `sync: false`，线上值只在 Render 面板里，仓库不可见；配错则全站请求失败且**服务端无报错** |

### 2.3 值得肯定的部分

- `crawler/registry.py` 的**元数据 + 适配器成对注册**（`CrawlerPlatform` + `BaseCrawlerAdapter`）已经非常接近 OpenAlice 的 ToolCenter 思路，是重构的好底子。
- `crawler/adapters/base.py` 的 `BaseOxylabsAdapter` 抽象得当，子类只需实现 `_build_search_url()` / `_platform_name()`。
- `analysis.py` 的五维评分模型（`ScoreLevel` / `DimensionScore` / `AnalysisResult`）是业务壁垒，应完整保留。

## 3. 可迁移 vs 不可迁移

### 3.1 ✅ 应当学习的架构模式

| OpenAlice 模式 | 它解决的问题 | 我们的用法 |
|---|---|---|
| **ToolCenter** 统一工具注册表 | 能力只注册一次，同时导出给 Agent 与 MCP | 合并我们现在**互不相通的两套 registry**（`tools/` 和 `crawler/`） |
| **ProviderRouter** + `ai-provider.json` | 运行时切换模型，不重启、不改码 | 干掉散落 3 处的 DeepSeek/Kimi 降级逻辑，收敛成一份配置 |
| **config 即数据**（JSON + Zod 校验 + 缺省回退） | 配置不进代码 | 我们散落 14 个 `os.getenv` → `config/*.json` + pydantic 校验 |
| **prompt 双层覆盖**（`default/` 提交进 git + 用户覆盖 gitignore） | 改 prompt 不动版本库 | 我们现在 prompt 硬编码在 4 个文件、前后端各一份 |
| **Workspace Issue 自调度**（`.alice/issues/*.md` + `when:` frontmatter） | 无需调度服务就能跑定时任务 | Store Pilot 从假数据 → 真·价格/差评/库存监控 |
| **Inbox**（报告回流 + 可回溯到产出会话） | 结果有归属、有来源 | 现在报告读完即丢，零留存 |
| **append-only JSONL 事件日志** | 崩溃可恢复、UI 可消费 | 直接解决 `TASK_STORE` 内存字典问题 |
| **sealing**（凭证静态加密） | 密钥不落明文 | 我们现在密钥直接发给浏览器 |
| **Docker 契约**：tini PID1、`/data` 持久卷、healthcheck、admin token、仅 loopback | 自托管可靠性 | 我们的 Dockerfile 无 healthcheck、无卷、无鉴权 |

### 3.2 ❌ 不该照搬的部分

| OpenAlice 的东西 | 为什么不适合我们 |
|---|---|
| CCXT / Alpaca / IBKR / OpenBB 行情与券商 | 完全不搭界，是它的业务领域 |
| Guardian 多进程监管 + PTY 会话 | 为"本地 spawn Agent CLI"而生；Serverless/容器单进程模型下无意义，成本极高 |
| 桌面端 Electron 分发 | 我们是 Web 产品，不是桌面软件 |
| 交易钱包（stage/commit/push）、Guard 风控 | 是"交易即 Git"的领域专用设计 |
| 事件总线 | **它自己都已经废弃了**，别去复刻 |

### 3.3 ⚖️ 许可证红线（重要）

OpenAlice 是 **AGPL-3.0**。这是**带网络条款的强 copyleft**：

> 只要你的服务通过网络向用户提供 AGPL 代码的功能，你就**必须**把整个服务的完整源码以 AGPL-3.0 公开。

对我们的影响：

- ✅ **可以**学习它的架构思想、设计模式、文档里的概念——**思想不受著作权保护**。
- ❌ **不可以**复制它的源代码。一旦复制，`VERTEX-PRO-V2` 就必须整体 AGPL-3.0 开源，且**所有使用者都有权索取我们全部源码**。对参赛/商业化项目是实质性风险。
- 📌 现在的 `VERTEX-pro` **没有 LICENSE**（GitHub 显示 `license: None`）。V2 必须主动选一个。

**执行原则：只读它的 `docs/` 和架构，不抄它的 `src/`。所有实现我们自己写。**

### 4.2 三个核心抽象

**① ToolCenter —— 一个注册表统治所有能力**

现状是两套平行注册表（`tools/registry.py` 的 4 个工具 + `crawler/registry.py` 的 7 个平台），互不相通。合并后：

```python
@dataclass
class ToolSpec:
    name: str                      # "jd.search"
    description: str               # 给 Agent 看的自然语言描述
    platform: str                  # "jd"
    capabilities: list[str]        # ["search", "detail", "comments"]
    required_env: list[str]        # ["EBAY_API_KEY"]
    handler: Callable
    health_check: Callable

class ToolCenter:
    def register(self, spec: ToolSpec) -> None: ...
    def get(self, name: str) -> ToolSpec | None: ...
    def list_for_agent(self) -> list[dict]:   # 导出 OpenAI function-calling 格式
    def list_health(self) -> list[dict]:      # 导出健康状态给 UI
```

**② ProviderRouter —— 干掉重复的降级逻辑**

DeepSeek→Kimi 降级现在**写了两遍**（`api/creative.py:141-166` 和 `lib/imageGenerator.ts:87-116`）。收敛成：

```json
// config/providers.json
{
  "chat":     [{"provider":"deepseek","model":"deepseek-chat"},
               {"provider":"kimi","model":"moonshot-v1-8k"}],
  "planning": [{"provider":"deepseek"}, {"provider":"kimi"}],
  "image":    [{"provider":"custom","base_url":"${IMAGE_API_BASE_URL}"}]
}
```

调用方只说"我要 chat"，路由按序尝试。**密钥只存在于服务端。**

**③ Issue 自调度 —— 让 Store Pilot 从假数据变成真能力**

这是本次重构**业务价值最高**的一项。当前 `/store-pilot` 的库存预警、差评提醒、清货建议全部来自 `demoDataStore.ts` 的合成数据。改造后：

```markdown
<!-- data/issues/price-watch-xxx.md -->
---
title: 竞品价格监控
when: { kind: cron, cron: "0 9 * * *", timezone: Asia/Shanghai }
agent: default
---
监控该商品在 1688/淘宝的竞品价格，跌幅超 5% 时写入 Inbox 并说明原因。
```

一个纯文本文件 = 一个定时任务。无需 Celery、无需 Redis、无需调度服务。`issues/scanner.py` 定期扫描 + 解析 frontmatter，`schedule.py` 判断是否到点，`runner.py` 执行并把结果投进 Inbox。

### 4.3 数据存储方案

OpenAlice **没有数据库**（纯文件）。我们现在**也没有**（内存 + localStorage）。

建议采用**混合方案**，理由如下：

| 数据 | 存储 | 理由 |
|---|---|---|
| 事件日志 | append-only JSONL | 学 OpenAlice：追加写、崩溃可恢复、天然可审计 |
| 会话历史 | JSONL（每会话一文件） | 同上，且便于按会话回溯 |
| Issue / 定时任务 | Markdown + frontmatter | 学 OpenAlice：人类可读可编辑，Agent 也能改 |
| Inbox 报告 | Markdown + 索引 | 同上 |
| 商家档案 / 商品 / 采集任务 | **Postgres（Render 托管或 Supabase）** | 需要查询、聚合、多租户隔离；JSONL 做不了 |
| 前端状态 | Zustand（仅 UI 态） | 业务数据不再存 localStorage |

> 一句话：**领域数据进库，运维轨迹进文件**。这正是 OpenAlice 的分工（`event-log.ts` 是"领域无关的 JSONL 日志工具"，其余走各自领域存储）。

## 7. 部署方案（Vercel 正解）

### 7.1 先纠正一个误解

你说"他没部署到 Vercel"——实际上 OpenAlice **用了** Vercel，但用途是：

```json
{
  "buildCommand": "pnpm exec turbo run build:demo --filter=open-alice-ui",
  "outputDirectory": "ui/dist",
  "framework": null,
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}
```

`framework: null` + `outputDirectory: ui/dist` + 全量 rewrite 到 `index.html` —— 这是**纯静态 SPA 演示壳**的典型特征。**没有任何后端逻辑**。

### 7.2 为什么智能体后端不能上 Vercel

| OpenAlice 的运行需求 | Vercel Serverless 的现实 |
|---|---|
| 常驻 Guardian 监管进程 | 无常驻进程 |
| `~/.openalice` / `/data` 持久状态 | 文件系统临时、只读 |
| spawn `claude` / `codex` PTY 子进程 | 不能起子进程、不能交互式 IO |
| 长时运行的定时调度 | 函数有时长上限 |
| 仅 loopback 的本地管理面 | 每个请求都是公网入口 |

**这不是 OpenAlice 的选择，是物理限制。**

### 7.3 我们应该怎么做

我们**已经是**正确形态（Vercel UI + Docker API），但接线是错的。修正方案：

```text
浏览器
 └── Vercel（Next.js）                       ← 唯一对外入口，同源
      ├── /            → 页面
      └── /api/proxy/* → next.config.ts rewrites → Render Docker API
```

`apps/web/next.config.ts` 加 rewrites：

```ts
const nextConfig: NextConfig = {
  async rewrites() {
    return [{
      source: '/api/proxy/:path*',
      destination: `${process.env.API_ORIGIN}/api/v1/:path*`,
    }]
  },
}
```

收益：

1. **消灭 CORS 那一整类故障**（不再需要 `ALLOWED_ORIGINS` 在 Render 面板里维护）
2. **后端地址不再硬编码在 `vercel.json`**（现在硬编码 `https://vertex-pro.onrender.com/api/v1`，改一次要提交一次）
3. 密钥全部留在服务端，浏览器只见同源请求
4. 未来要加鉴权，只需在 Next.js 中间件拦截

### 7.4 后端容器契约（对齐 OpenAlice 的 Docker 规范）

```dockerfile
# 要点
- tini 作 PID 1（正确转发信号、回收僵尸进程）
- 非 root 用户运行
- HEALTHCHECK 打 /health
- 持久状态统一挂 /data（DATA_HOME=/data）
```

```yaml
# docker-compose.yml 要点
- restart: unless-stopped
- stop_grace_period: 30s
- 只暴露必要端口
- 日志轮转 max-size: 10m / max-file: 3
- volume: vertex-data:/data
```

这些**全部直接来自 OpenAlice 的 `docker-compose.yml` 与 `docs/docker-deployment.md`**——这是它最值得抄的工程实践。

## 9. 风险与取舍

| 风险 | 说明 | 应对 |
|---|---|---|
| **许可证污染** | 参考 AGPL 代码会让 V2 被迫 AGPL 开源 | 只读文档不抄代码；V2 主动选 MIT/Apache-2.0 |
| **追不上移动靶** | OpenAlice 一天前还在推送，架构持续变（事件总线已废弃） | 学设计意图，不追实现细节 |
| **过度工程** | Guardian 多进程、PTY、钱包体系对我们是纯负担 | 明确不做（§3.2） |
| **重构期功能回退** | 边重构边掉功能 | 每个 Phase 独立可发布；五维分析等核心资产零改动 |
| **Phase 0 被跳过** | 直接上架构，漏洞原样搬家 | Phase 0 设为硬门槛 |
| **Postgres 引入成本** | 目前零数据库，一步到位有迁移量 | 先 JSONL 满足会话/事件/Issue，Postgres 只承载需要查询的领域表 |
